# MemoryPlace 제품·기술 설계

작성일: 2026-09-28 · 상태: 핵심 기능 구현, 실기기 성능·운영 배포 검증 전

## 1. 제품 정의

MemoryPlace는 메모를 **3D 뉴런 그래프**에서 탐색하고, 선택한 메모를 **줄이 있는 종이 페이지**에서 읽고 쓰는 웹 앱이다. 두 화면은 같은 메모 데이터를 공유한다. 그래프는 관계와 위치를 보여주고, 페이지는 긴 글 편집에 집중한다.

참고 영상: [Instagram 릴](https://www.instagram.com/reel/DVlmQXkAgy3/?utm_source=popular_topic_grid). 확인된 특징은 어두운 배경, 흰색·초록색 텍스트가 붙은 연결 그래프, 3D 회전·확대 탐색과 생각의 군집이다. 정확한 셰이더와 원본 데이터 처리 방식은 영상만으로 확인할 수 없으므로 동일 구현을 전제하지 않는다. 영상 설명에는 Obsidian 노트의 임베딩과 force-directed 네트워크가 언급되지만, MemoryPlace의 첫 버전은 사용자가 만든 링크와 제목 검색을 우선한다. 의미 기반 자동 연결은 성능·품질 검증 후 추가한다.

### 핵심 동작

1. 로그인 후 보드를 열면 저장된 시점과 위치에서 뉴런 그래프가 나타난다.
2. 노드를 만들고 제목·본문을 입력한다. 노드 사이를 연결하거나 연결을 끊는다.
3. 노드를 선택해 위치를 끌어 옮기거나 크기를 조절한다. 수동으로 옮긴 좌표는 고정해 저장한다.
4. 노드를 열면 페이지 모드에서 같은 본문을 줄이 있는 흰 종이 형태로 편집한다.
5. 모드를 바꿔도 선택 노드, 작성 내용, 카메라 위치가 유지된다. 자동 저장 상태를 표시하고 실패 시 재시도한다.

## 2. 기술 선택

| 계층 | 선택 | 선택 이유 |
|---|---|---|
| 언어 | TypeScript | 프런트엔드와 API의 자료형·검증 모델 공유 |
| UI | React + Vite | 로그인, 도구막대, 페이지 편집 같은 일반 UI에 사용 |
| 3D 렌더링 | Three.js의 WebGL2 렌더러를 직접 제어 | 브라우저 GPU에서 노드·링크를 일괄 렌더링하고 프레임을 세밀하게 제어 |
| 배치 계산 | Web Worker + 3D force layout | 대량 좌표 계산이 입력 처리를 막지 않도록 분리 |
| API | Node.js + Fastify + MongoDB 공식 드라이버 | 작은 HTTP 계층, 배치 저장과 부분 그래프 조회를 명시적으로 제어 |
| DB | MongoDB 8.0 컨테이너 | 사용자 요청에 맞춘 저장소. 메모 본문과 그래프 메타데이터를 별도 컬렉션으로 관리 |

여기서 **벡터**는 노드·선·좌표를 벡터 데이터로 유지하고 GPU가 그린다는 뜻이다. 노드마다 HTML/SVG 요소를 만드는 방식은 채택하지 않는다. 화면에는 WebGL `<canvas>` 하나와 소수의 입력·접근성 UI만 둔다. WebGL은 내부적으로 화면을 픽셀로 출력하므로 “벡터 = 어떤 확대율에서도 렌더 비용이 0”을 의미하지 않는다.

Three.js `InstancedMesh`는 같은 형상을 한 번에 그려 draw call을 줄이는 기능을 제공한다. [공식 문서](https://threejs.org/docs/pages/InstancedMesh.html). 초기 렌더러는 검증 범위가 넓은 WebGL2를 쓰고 WebGPU 전환은 실측 결과가 이득을 보일 때 결정한다. 현재 Three.js WebGLRenderer는 WebGL2를 사용한다. [공식 문서](https://threejs.org/docs/pages/WebGLRenderer.html).

## 3. 화면과 입력 설계

### 뉴런 모드

- 검은색에 가까운 배경, 깊이에 따른 밝기 변화, 노드의 약한 발광, 선을 따라 흐르는 제한된 수의 점으로 뉴런 느낌을 만든다.
- 노드는 제목과 미리보기 한 줄을 가진다. 가까운 노드·선택 노드에만 제목을 표시한다. 멀리 있는 노드는 점이나 군집으로 축약한다.
- 연결은 굵기와 색으로 관계를 표현한다. 활성 노드와 이웃 연결만 강조한다.
- 처음 열 때는 저장된 좌표를 즉시 보여준다. force layout은 새 노드와 주변 노드만 단계적으로 계산하며, 전체 그래프의 지속적인 흔들림은 막는다.
- 카메라는 회전·이동·확대를 지원한다. 노드를 선택하면 연결된 이웃으로 부드럽게 초점을 옮길 수 있다.

### 페이지 모드

- 선택한 메모의 제목과 본문을 흰 종이, 연한 파란 가로줄, 왼쪽 여백선 위에 표시한다.
- 긴 본문은 하나의 편집 영역으로 다룬다. 줄무늬는 CSS 배경으로 그려 노트 줄마다 DOM 요소가 생기지 않게 한다.
- 모바일에서는 키보드가 올라와도 커서가 보이도록 스크롤 영역을 조정한다. 본문 저장은 입력 중 디바운스하고 화면 이탈 시 즉시 전송한다.

### 제스처 규칙

| 상황 | 데스크톱 | 모바일 |
|---|---|---|
| 빈 공간 이동 | 왼쪽 끌기: 회전, 보조 끌기: 평행 이동, 휠: 카메라 확대 | 한 손가락: 회전, 두 손가락 함께 이동: 평행 이동, 핀치: 카메라 확대 |
| 노드 선택·이동 | 클릭: 선택, 선택한 노드 끌기: 3D 평면 위 이동 | 탭: 선택, 선택한 노드 한 손가락 끌기: 이동 |
| 노드 크기 | 선택 노드의 크기 손잡이 끌기 또는 속성 패널 | 선택 노드 위 두 손가락 핀치: **노드 자체** 확대·축소 |
| 본문 열기 | 더블클릭 또는 열기 버튼 | 선택 후 열기 버튼 또는 두 번 탭 |

선택 노드 위 핀치와 빈 공간 핀치를 구분해, 노드 크기와 카메라 확대가 혼동되지 않게 한다. 노드를 이동할 때는 카메라와 평행한 평면과 포인터 광선의 교점을 이용한다. 노드 크기는 예를 들어 0.5~3배로 제한하고 접근성을 위해 동일 기능을 버튼에도 제공한다. 모바일 입력은 Pointer Events와 pointer capture를 사용하고, 제스처별 `touch-action`을 테스트한다.

## 4. 성능 구조

1. **화면 개수 제한:** 노드 구체는 재질별 `InstancedMesh`, 링크는 변경 가능한 큰 선 버퍼로 묶는다. 노드마다 React 컴포넌트나 별도 Mesh를 만들지 않는다.
2. **보이는 것만 전송:** API는 보드 요약, 카메라 주변 하위 그래프, 선택 노드 본문을 나눠 제공한다. 본문 전체를 그래프 첫 화면에 싣지 않는다.
3. **수준별 표시:** 화면 밖 노드·링크를 제외하고, 멀리 있는 노드는 군집으로 대체한다. 모바일은 군집 전환 거리와 보이는 라벨 수를 더 보수적으로 설정한다.
4. **레이아웃 분리:** force layout과 군집 계산은 Worker에서 한다. 대량 배열은 `Float32Array` 등으로 전달하고, 드래그 중 해당 노드와 인접 링크만 갱신한다.
5. **그릴 때만 그리기:** 입력·카메라 관성·선택 효과가 없으면 프레임 루프를 멈춘다. 움직일 때도 애니메이션 점·글로우를 품질 단계에 따라 줄인다.
6. **화질 자동 조정:** 기기 픽셀 비율에 상한을 두고, 최근 프레임 시간에 따라 내부 해상도·라벨 밀도·효과를 낮춘다. 기본 모바일 설정은 실시간 그림자와 화면 전체 bloom을 쓰지 않는다.
7. **텍스트 비용 제한:** 보이는 제목만 글리프 아틀라스로 그린다. 본문 편집용 DOM은 페이지 모드 또는 선택한 노드의 팝오버에만 둔다.
8. **입력과 저장 분리:** 드래그·핀치는 클라이언트가 즉시 처리한다. 저장 요청은 마지막 좌표를 묶어 보내고, 서버 응답을 기다리며 포인터를 멈추지 않는다.

현재 구현에는 `InstancedMesh` 노드·발광 효과, 하나로 묶은 링크 선, 변경이 있을 때만 그리는 루프, 픽셀 비율 상한과 느린 프레임 감지, 최대 36개 제목을 그리는 2D Canvas 레이어가 들어 있다. 새 노드의 배치 계산은 Worker로 분리했다. 군집 묶기·제목 그리기와 3D 포인터 판정은 아직 메인 스레드에서 수행한다. 시야 밖 개별 노드의 전송 제외, 글리프 아틀라스, 링크를 따라 흐르는 점과 모바일 실기기 성능 시험은 후속 성능 작업이다. 초기 그래프는 1,500개씩 가져오며 본문은 메모를 열 때만 읽는다.

`OffscreenCanvas`는 렌더링을 Worker로 옮길 수 있지만 일부 사용 방식의 지원 범위가 달라 초기 필수 경로로 두지 않는다. 우선 레이아웃 Worker와 메인 스레드 WebGL로 측정하고, 입력 지연이 남을 때 지원 기기를 대상으로 렌더 Worker를 실험한다. [MDN 문서](https://developer.mozilla.org/en-US/docs/Web/API/OffscreenCanvas).

### 검증 가능한 성능 목표

“절대 버벅이지 않음”은 기기·브라우저·데이터 크기에 관계없이 보장할 수 없다. 다음은 구현 전 **목표값**이며 실측 결과가 아니다.

| 시험 장면 | 합격 목표 | 조치 |
|---|---|---|
| 현대적 데스크톱, 노드 5,000개·링크 10,000개 | 회전·확대 중 프레임 시간 p95 ≤ 16.7ms | 군집·라벨 제한이 적용된 화면 |
| 기준 모바일(iPhone 13 Safari, Galaxy A54 Chrome), 노드 1,000개·링크 3,000개 | 조작 중 프레임 시간 p95 ≤ 33.3ms, 입력 반응 p95 ≤ 50ms | 발광·해상도 자동 조절 |
| 기준 모바일, 노드 10,000개·링크 20,000개 저장된 보드 | 초기 화면은 3초 이내 조작 가능, 군집 탐색 중 p95 ≤ 33.3ms | 전체를 한 번에 렌더링하지 않음 |
| 네트워크 재연결 | 로컬의 마지막 편집이 보이고 복구 후 저장 재시도 | 충돌 상태는 사용자에게 표시 |

기준은 실제 기기에서 Chrome/Safari 성능 기록과 앱 내부의 p50/p95 프레임 시간, 입력 시각→화면 반영 시각, draw call, GPU 메모리, 첫 조작 가능 시간을 측정한다. 합격 전에는 “항상 60fps”라고 광고하지 않는다. 저전력 모드와 열 제한 상태도 별도로 측정한다.

## 5. 데이터와 API

```text
users:  { _id, username, passwordHash, role, mustChangePassword, createdAt }
boards: { _id, ownerId, title, cameraState, revision, createdAt, updatedAt }
notes:  { _id, boardId, title, body, createdAt, updatedAt, revision }
nodes:  { _id, boardId, noteId, x, y, z, scale, color, pinned, updatedAt }
edges:  { _id, boardId, sourceNodeId, targetNodeId, kind, weight, createdAt }
```

본문과 좌표를 분리해 움직일 때 긴 본문을 다시 쓰지 않는다. 보드별 노드 조회, 메모 조회, 링크 양 끝점 조회를 위한 인덱스를 둔다. `(boardId, sourceNodeId, targetNodeId)` 고유 인덱스로 같은 링크 중복을 막는다. 사용자명도 고유 인덱스로 보호한다. MongoDB 고유 인덱스 동작은 [공식 문서](https://www.mongodb.com/docs/manual/core/index-unique/)를 따른다.

API 초안: `POST /auth/login`, `POST /auth/logout`, `PATCH /auth/password`, `GET /boards`, `POST /boards`, `GET /boards/:id/graph?focus=&depth=`, `POST /boards/:id/notes`, `GET/PATCH /notes/:id`, `PATCH /boards/:id/nodes/:id`, `POST/DELETE /boards/:id/edges`. 모든 쓰기는 사용자·보드 소유권과 입력 크기를 검증한다. 드래그 저장은 최종 위치만 전송하되 `revision`으로 오래된 응답이 최근 위치를 덮지 못하게 한다.

첫 버전은 단일 사용자 또는 소수 사용자 환경으로 설계한다. 협업 동시 편집, 이미지 첨부, 자동 임베딩 연결은 별도 단계다.

## 6. 로그인과 보안

- 첫 실행 시 앱 계정 `admin / 1234`를 한 번만 생성한다. 비밀번호는 Argon2id 해시로 저장하고 첫 로그인 직후 변경 화면을 요구한다. 변경 전에는 메모 API 접근을 제한한다.
- 로그인 세션은 `HttpOnly`, `Secure`, `SameSite=Lax` 쿠키로 관리한다. 로그인 시도 제한과 세션 만료를 적용한다. HTTPS 없는 외부 접속에는 쿠키를 발급하지 않는다.
- **앱의 `admin / 1234`와 MongoDB 관리자 암호는 완전히 분리한다.** MongoDB 암호는 서버에서 무작위 생성하며 Git에 넣지 않는다.
- MongoDB는 인증을 켜고 데이터 볼륨을 사용한다. 개발 초기에는 호스트 `127.0.0.1:27019`에만 바인딩한다. 외부 API 서버에서 필요하면 SSH 터널 또는 VPN 내부 통신을 사용하고 DB 포트를 인터넷에 개방하지 않는다. [MongoDB 보안 지침](https://www.mongodb.com/docs/manual/administration/security-checklist/).
- 백업은 정기 `mongodump`와 복구 연습을 배포 단계에 포함한다. 사용자 데이터가 생기기 전 보존 주기와 저장 위치를 확정한다.

## 7. 배포와 저장소

- 원격 저장소: <https://github.com/kyoungrae/MemoryPlace.git>
- DB 대상: 운영자가 지정한 SSH 장비의 Docker Desktop. 실제 호스트 주소와 SSH 계정은 저장소에 기록하지 않는다.
- DB 정의: [`../infra/mongo/compose.yaml`](../infra/mongo/compose.yaml). 데이터는 Docker 명명 볼륨에 보관하고 비밀번호 파일은 저장소 밖에 둔다.
- 2026-09-28 배포 확인: `memoryplace-mongo` 실행, 인증된 `ping` 성공. 실제 운영 파일 경로와 암호는 저장소 밖에서 관리한다.
- 웹/API 배포는 아직 정하지 않았다. 성능에 영향을 주는 핵심은 클라이언트 GPU 경로이므로, 호스팅 선택 전에 3D 조작 프로토타입을 실기기에서 측정한다.

```text
브라우저 ── HTTPS ── API ── MongoDB
   │                  │
   └─ WebGL2 GPU      └─ 보드별 부분 그래프 조회
      + 레이아웃 Worker
```

## 8. 구현 순서와 완료 기준

1. **렌더 프로토타입:** 가짜 노드 1천/5천/1만 개로 3D 회전, 선택, 드래그, 핀치와 프레임 시간을 검증한다. 목표를 못 맞추면 비주얼보다 배칭·군집 설계를 먼저 바꾼다.
2. **메모 기본기:** 계정, 보드, 노트, 링크, 저장된 좌표, 페이지 편집과 자동 저장을 연결한다.
3. **뉴런 표현:** 깊이, 강조, 제한된 애니메이션, 라벨 수준별 표시를 추가한다.
4. **모바일 검증:** 두 종류 이상의 실기기에서 조작 충돌, 키보드, 배터리, 열 제한 상태를 확인한다.
5. **운영 준비:** 백업·복구, HTTPS, 오류 기록, 비밀번호 변경, 데이터 내보내기 기능을 확인한다.

첫 출시 완료 조건은 로그인·메모 작성·링크·두 모드 전환·모바일 노드 이동 및 핀치 크기 조절·저장 복구가 작동하고, 위 성능 시험을 통과하는 것이다.

## 9. 확정이 필요한 제품 결정

- 노드가 자유 배치된 **하나의 보드**가 기본인지, 주제별 여러 보드가 기본인지: 데이터 구조는 여러 보드를 허용하고 첫 화면은 하나의 기본 보드로 시작한다.
- 임베딩 기반 자동 연결의 필요성: 참고 영상에 등장하지만 첫 출시 범위에서는 제외한다. 사용자가 직접 만든 연결만 확실히 보여준다.
- 외부 접속 방식: 웹/API의 호스팅과 도메인이 정해지면 MongoDB 연결 경로와 HTTPS 구성을 확정한다.
